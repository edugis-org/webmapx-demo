## what

The GIS operations that take a layer or two, a few parameters, and produce a new
layer. Clip, erase, intersect, union, select by location, spatial join,
dissolve, centroid, convex hull, simplify, buffer, voronoi, delaunay, cartogram
— and statistics, which is a dissolve without the geometry.

They are one panel rather than fourteen tools because they are one pipeline:
one or two layers in, a few parameters, one result out. Choosing an operation
collapses the grid to a chip and the inputs appear below it. It is progressive
disclosure, deliberately not a wizard — a wizard with a back button loses the
parameters you already set.

A few of the choices are worth knowing:

- **Clip and intersect differ in feature count, not shape.** Clip merges the
  overlay first, so one input feature stays one output feature carrying its own
  attributes. Intersect runs per overlapping pair, so a feature meeting three
  others becomes three, each carrying that other's attributes.
- **Simplify keeps shared borders shared.** Simplifying each polygon on its own
  simplifies a common boundary twice, differently, and leaves slivers between
  neighbours. This builds a topology first, so both sides keep identical points.
- **Attribute aggregation is a parameter, not an operation** — sum, mean, min,
  max, count, and a list. `total` and `average` are hidden for a field not
  observed to hold numbers, because summing text in SQL silently returns
  nonsense rather than an error.

Everything runs in the browser, in GDAL compiled to WebAssembly. No data is
uploaded.

## use

1. Choose an operation. Its inputs and parameters appear.
2. Pick the layers, set the parameters, press **Calculate**.
3. The result is added as a new layer, and reports how many features it
   consumed.

**What goes in is what the map has drawn**, and the panel warns where that
matters: a GeoJSON layer contributes every feature, a tile-backed layer only
what is in view. The warning appears under those inputs alone — a warning on
every input is one people learn to ignore.

Three companion pages work the operations through on real data. All three are
generated by *running* the operations, so they show what the code does rather
than what it is meant to do:

- **[Two-layer operations](./analysis-operations.html)** — five countries and one
  rectangle through clip, erase, intersect, union, select by location and
  spatial join, with the geometry *and* the attributes that come out of each.
- **[One-layer operations](./analysis-single-layer.html)** — dissolve,
  statistics, centroid, label point, buffer, convex hull, simplify, cartogram,
  voronoi and delaunay on the same five countries.
- **[Which geometry each operation takes](./analysis-geometry.html)** — points,
  lines and polygons against every operation, measured combination by
  combination, because nothing in the configuration declares it.

A long calculation can be **cancelled**. Union is the expensive one: on 257
countries against 4000 regions, clip took 4 s, intersect 5 s and union 38 s.

## embed

Add `geoprocessing` to a toolbar; it appears as **Analysis**. It works on
whatever layers are on the map.

The WebAssembly is fetched on first use, so a visitor who never opens the panel
never downloads it. Opening the panel starts that load in the background while
you fill in the form.

## extend

An operation is a registry entry — its inputs, its parameters, and either an
SQL template or a JS function — plus a diagram. Adding one is data, not UI work,
and a missing diagram is a compile error.

Everything runs in EPSG:3857 rather than lon/lat, because SpatiaLite's
predicates are planar and a tolerance in degrees means different distances at
different latitudes. Inputs are materialised into one indexed SpatiaLite
database before the SQL runs: on 144×576 polygons that took a query from 19.8 s
to 1.3 s, and the algorithm was never the bottleneck.
